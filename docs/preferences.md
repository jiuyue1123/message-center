# 用户偏好、频控、回执与里程碑

本文描述两件事：消息是否应当发送，以及发出之后发生了什么。

## 一、两阶段求值

偏好判定发生在两个时刻。检查放错阶段会产生代价高且难以定位的缺陷。

| 阶段 | 判定内容 | 违反后果 | 动作 |
|---|---|---|---|
| 接收时 | 通道退订、按 `biz_type` 退订、地址抑制 | 消息不应存在 | 不创建投递，或创建为 `skipped` |
| claim 时 | 免打扰、频控 | 消息此刻不应发送 | `Release` 到未来时刻，不消耗重试次数 |

硬偏好必须在接收时判定：违反硬偏好的消息若进入发送阶段，会产生永远无法成功的投递记录，占用重试预算并计入错误率，而它本应是一条正常的 skip。

时间性偏好必须在 claim 时判定，因为它取决于消息的实际发送时刻，而该时刻与提交时刻不同：

- 15:00 提交、定于 22:30 发送的消息
- 被免打扰延后过一次、醒来时已进入次日窗口的消息
- 失败后重试至凌晨的消息

仅在接收时判定会使所有定时消息在错误时间发出。

## 二、免打扰

```go
type QuietHours struct {
    StartMinute      int
    EndMinute        int
    Days             []time.Weekday
    ExemptBizTypes   []string
    ExemptChannels   message.ChannelSet
    ExemptPriorities []message.Priority
}
```

### 时区

免打扰描述的是用户的本地时间，因此按用户时区求值，不按服务器时区。服务器在 UTC 而按 UTC 求值 22:00-08:00 窗口，会使一个 Asia/Shanghai 用户从本地 06:00 被静音到 16:00，且从服务器侧无法察觉。`Active` 要求显式传入 `*time.Location`，使转换无法被遗漏。

### 跨午夜

常见配置是 22:00 到 08:00，跨午夜。`now.After(22:00) && now.Before(08:00)` 对任何时刻均为 false，会使该功能对最常见的窗口形态失效。`StartMinute > EndMinute` 即跨午夜，代码中单独处理。

### 豁免

`ExemptBizTypes` 用于让重置密码、验证码、风控告警在凌晨送达。缺少豁免路径时，免打扰最终会挡住用户急需的消息，修法往往是整体关闭该功能。

### 延后目标

`NextEnd` 返回当前窗口的结束时刻，直接作为 `NextAttemptAt`：

- 给晚，消息在用户醒来之后才到达
- 给早，窗口仍在生效，会再延后一次，正确但多消耗一个 claim 周期

对按星期几限制的窗口，计算出的结束时刻可能落在窗口不运行的那天。`NextEnd` 会逐日推进直到窗口真正结束，上限一周。

## 三、频控

```go
type CapRule struct {
    Name    string
    Scope   CapScope
    Window  time.Duration
    Max     int
    Action  CapAction
}
```

### 滑动窗口

采用滑动窗口而非固定窗口。固定窗口允许用户在边界两侧连续获得两份配额（23:59 收到 100 条，00:00 再收到 100 条），正是频控要防止的突发。`MemCounter` 因此存储每次事件的时间戳，而非计数器加窗口起点。

### 动作选择

| 动作 | 适用 | 理由 |
|---|---|---|
| `drop` | 营销类 | 迟到三天的促销劣于不送达，且会促使用户退订 |
| `defer` | 事务类 | 订单更新延后优于不发，前提是 `ExpiresAt` 允许 |

两者都记录为 `skipped`，不计为 failed。

### 计数器的实现要求

计数器必须跨副本共享。进程内计数器只限制单个进程，N 个副本下实际额度为配置值的 N 倍。`preference.MemCounter` 仅适用于单副本部署。

check 与 increment 必须为同一操作。`Counter` 只提供 `IncrIfBelow`，不提供分离的读与写：分离的接口会诱导调用方"读取、判断未超限、写入"，而两个 worker 并发执行该序列时会同时判定未超限。

超过上限时仍需递增，否则计数器无法反映真实量级，建立在其上的告警、公平份额和渐进限流都会在上限处失明。

计数器返回错误时（通常为共享存储不可达），`StaticEvaluator` 返回错误使投递重试，而非放行。放行等同于在依赖故障时静默关闭频控。

## 四、回执与里程碑

### 不并入状态枚举的原因

回执具有以下性质：乱序到达（收件人可能先点击链接，打开像素后上报）、重复到达（webhook 重试）、以及退信可能在送达回执未到达时先到。线性状态机无法表达，强行并入会使迁移表必须允许 `read → delivered` 和 `delivered → delivered`。

因此回执按行存储为事实，投递行只保留派生摘要。

### 派生字段

```go
Milestone     // none < delivered < read < clicked，单调
Bounced       // BounceType，正交
ComplainedAt  // 正交
LastReceiptAt // 用于发现服务商回调停止
ReadAt        // 站内信未读数依赖它走覆盖索引
```

唯一正确的应用方式是 `Delivery.ApplyReceipt`，单调且幂等。直接赋值会在服务商乱序发送回执时把已点击的投递退回已送达，使漏斗报表以一种看似数据问题的方式出错。

单调性由 `MilestoneFor` 的第二个返回值保证：退信、投诉、退订、拒绝是发生在消息上的事件，不是消息经过的阶段，调用方无法写出让它们推进漏斗的代码。

### 退信类型

| 类型 | 含义 | 动作 |
|---|---|---|
| `hard` | 地址不存在 | 抑制该地址 |
| `soft` | 暂时性 | 保留地址 |
| `unknown` | 服务商未说明 | 按 soft 处理 |

`unknown` 按 soft 处理，因为抑制有效地址是更严重的错误。`ApplyReceipt` 允许 soft 升级为 hard，不允许 hard 降级为 soft：抑制决策读取该字段，降级会使本应被抑制的地址重新开始收信。

### 各通道可获得的回执

| 通道 | accepted | delivered | read | clicked | bounced | complained |
|---|:--:|:--:|:--:|:--:|:--:|:--:|
| 站内信 | 是 | 是（写库即送达） | 是（客户端上报） | 是 | 否 | 否 |
| 移动 Push | 是 | 部分平台 | 否 | 是 | 否 | 否 |
| 邮件 | 是 | 是 | 不可靠（打开像素可被隐私代理代取） | 是 | 是 | 是 |
| 短信 | 是 | 是 | 否 | 短链 | 否 | 否 |
| Webhook | 是 | 是（HTTP 2xx） | 否 | 否 | 否 | 否 |

该表对应 `Capabilities.SupportsReceipts`。面向用户的文案中，不得将"已送达"表述为"用户已看到"。

### 幂等

服务商会重试 webhook。不幂等的回执处理器会在服务商抖动时重复记录同一回执，灌水漏斗，并在退信路径上重复下发抑制。

`Receipt.DedupKey()` 优先使用服务商事件 ID，否则使用 `(delivery, kind, 事件时间, bounce 类型)` 自然键。store 对其建唯一约束，重复时返回 `mcerr.ErrConflict` 而非静默成功，使调用方能区分"已记录"与"已存在"，其比例即服务商重试频率。

自然键在服务商更换时间戳重放同一封退信时会产生重复行。这是可接受的，因为派生的 `Milestone` 幂等，且消费者只读 `Milestone`。

### 漏斗自检

`FunnelCounts` 的字段层层包含（Read ⊆ Delivered ⊆ Sent）。`Validate` 在 `read > delivered` 时报错，该现象是里程碑被赋值而非被推进的特征。

## 五、偏好存储

`preference.Store` 独立于 `store.Store`。偏好是最可能已存在于部署中的那部分数据（常见形态是用户表上的通知设置列），纳入消息中心自己的 Store 意味着复制一份已存在于别处的数据。

```go
type Store interface {
    Get(ctx, tenantID, userID) (*Preference, error)
    Put(ctx, *Preference) error
    SuppressAddress(ctx, tenantID, userID, addr, at) error
}
```

两处签名上的取舍：

- `Get` 对"无记录"返回空 `Preference` 与 nil error，而非 `ErrNotFound`。常见情况是用户从未打开设置页，让每个此类用户、每条消息都走错误路径并迫使每个调用方写 `errors.Is` 判断，代价不合理。
- `SuppressAddress` 是独立方法而非 `Get` 后 `Put`。退信 webhook 会为同一用户并发调用，读改写会丢失除一个以外的全部抑制。

## 六、待决策

1. **免打扰 `Days` 的语义**。目前指窗口开始的那天，"仅周末 22:00-08:00"覆盖周六 22:00 至周日 08:00。设置界面文案需要与此一致。

2. **频控在发送失败时是否退还配额**。目前不退还：计数发生在 `Evaluate`，消息随后发送失败仍占用额度。使计数与发送原子化不现实。代价是服务商故障会占用用户当日额度；替代方案（发送成功后再计数）会使突发重试灌水配额。当前选择前者。

3. **邮件已读回执的合规问题**。开信像素在部分司法辖区需要用户同意。当前将其记为 `read` 并标注不可靠，但未实现同意管理，面向欧盟用户投产前需法务确认。

4. **投诉缺少自动降级**。`ComplainedAt` 已记录，但"投诉后自动关闭该用户的营销通道"未实现。多数 ESP 要求配置投诉率阈值动作，接入真实服务商前需要补齐。
