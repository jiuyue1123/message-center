# 已知问题与待决策事项

按预计影响排序。本清单列出的是当前设计尚未解决的问题。

## 1. 幂等键的保留期

唯一索引为 `(tenant_id, idempotency_key)`，因此键按租户永久唯一，除非使其过期。当前选择永久不过期，这一选择尚未经过验证。

引入 TTL 需要二选一：使用 sweeper 将旧键置 NULL（会破坏"同一请求永远重放同一条消息"的保证），或增加一张带独立过期时间的 `idempotency_keys` 表。上线前需要决定。

重复路径必须通过捕获 INSERT 的唯一键冲突实现，不能先 `SELECT` 再 `INSERT`。后者在并发相同提交下会竞态：两个客户端同时重试同一请求，双方均认为不存在已存行，双方均插入。

## 2. 投递语义为至少一次

worker 可能在服务商已接收但 `CommitAttempt` 未写入时崩溃。投递停在 `sending` 直到租约过期，随后被回收重试，用户收到两份。

唯一缓解手段是 `SendRequest.DedupKey()`，由支持幂等键的服务商去重。不支持的服务商需要 Sender 自行对照服务商侧记录。

任何文档中都不得宣称恰好一次。

## 3. 站内信与广播

站内信的传输层是 `deliveries` 表，投递行同时是工作项、尝试记录和收件箱行。这带来零双写、未读数单一来源、收件箱分页复用投递表。

代价是广播未解决：向 100 万用户发送即产生 100 万行投递。

改进方案是增加 `broadcasts` 表并在首次读取收件箱时惰性物化。若广播在路线图上，本设计需要第四层（Message → Broadcast → Delivery），事后补充成本较高。需要尽早确认。

## 4. 缺少完成通知

`partially_succeeded` 加每投递状态数组是当前的上报方式。没有"全部通道必须成功否则整体失败"的开关，这是有意的：需要跨通道依赖的调用方需要的是工作流。

问题在于客户端会在提交后密集轮询 `GET /messages/:id`，且总会先看到 `pending`。

为 `Message` 增加 `callback_url` 并在终态回调是成本较低的改进。推迟该改动意味着后续每个已有客户端都在轮询。

## 5. 三个恢复机制尚未实现

队列是加速器，`deliveries` 表是真相。三个机制必须同时存在：

| 机制 | 缺失后果 |
|---|---|
| Sweeper：周期 `ClaimDue` 并重新入队 | 队列丢弃的投递永久搁浅 |
| Reclaimer：启动时及周期 `ReclaimExpiredLeases` | 每次崩溃永久搁浅该进程正在处理的投递 |
| Scheduler：周期 `ListDueScheduled` | 停机期间到点的定时消息丢失 |

三者尚未实现，且都是必选项。

## 6. 进程内限流与进程内频控在多副本下失效

限流：每个副本持有独立的令牌桶，N 个副本各按满速发送，实际速率为配置值的 N 倍。`Limiter` 的默认实现是 `Unlimited`，该默认值对生产环境不合适。

频控：同一问题。`preference.MemCounter` 仅适用于单副本。

两件事需要同时落地：共享计数器（Redis）以及通过 `KindRateLimited` 响应服务商的 429。

限流拒绝不得消耗重试次数，它走 `Release` 而非 `CommitAttempt`。误用会使一波流量在没有任何服务商调用的情况下耗尽所有投递的重试预算，且"三次尝试后全部失败"这一现象难以追溯到限流器。

## 7. 已接收与已送达的区分依赖实现纪律

`DeliveryStatus` 止于 `accepted`。其后的一切由 `Milestone` 与 `Receipt` 表达，二者单调、容忍乱序和重复。

需要保持的约束：

- 不为 `d.Milestone` 直接赋值，只使用 `Advance`。直接赋值是漏斗报表出错（已读率高于送达率）的唯一来源。
- 在看板上运行 `FunnelCounts.Validate`，它检测的正是上述违规。
- 面向用户的文案中，不将"已送达"表述为"用户已看到"。

本设计没有 `delivered` 状态。增加它会改变枚举，并影响每个未写 `default` 分支的 `switch`。因此它是 `Milestone` 而非 status。

## 8. 跨通道没有顺序保证

每投递的尝试按 `attempt_no` 有序，收件箱按 `(created_at DESC, id DESC)` 有序。

一条消息扇出到多个通道后，通道之间没有顺序。带 `scheduled_at` 的消息在 ticker 发现时触发。

若产品需求是"push 必须先于邮件到达"，那需要工作流引擎。消息中心无法提供该保证，强行模拟会在压力下产生难以定位的缺陷。

## 9. attempts 与 receipts 表的增长

两张表都只追加。`delivery_receipts` 在邮件通道量最大，一次发送可能产生 delivered、read、clicked 三行。

分区不解决单表插入热点。两张表在数月内会达到一亿行量级，需要归档路径或迁移到只追加日志。

任何界面中都不应对它们执行 `COUNT(*)`。报表读取聚合表，或读取 `deliveries` 上派生的 `milestone`。

## 10. PII 分布

出现在 `messages.recipient` JSON、`deliveries.address_value`、`delivery_attempts.response_snippet`、`delivery_receipts.url/user_agent/ip`。

需要在当前阶段确定的规则：

1. 所有 HTTP 响应中脱敏地址，使用 `message.Address.Masked`。
2. 不存储服务商原始响应体，只存请求摘要与截断脱敏后的响应片段。服务商响应常回显完整请求，包含收件人地址与消息正文。
3. 日志 helper 接收 `Recipient` 并自行脱敏，不接收 `string`。接收字符串的 helper 无法区分邮箱与模板正文。
4. 规划硬删除路径。单个用户的数据删除请求是跨多表删除，没有天然的级联。

第 3 条最容易违反，它要求 API 设计上不提供犯错的可能。

## 11. 定时消息在提交时不物化投递

`ScheduledAt` 在未来时，不创建投递行，只存 `Message{status: scheduled}`。

理由：在提交时解析设备 token 或邮箱并保存三天，意味着向可能已不属于收件人的地址发送。

代价是扇出逻辑有两个调用点（`Submit` 与 `MaterializeScheduled`），因此必须只有一份实现。

## 12. 接收时渲染，不重渲染

模板在接收与第三次重试之间被编辑时，不得改变最终发送的内容。因此 `deliveries.content` 是完整快照，模板按版本不可变。

代价是存储冗余，以及修改模板无法影响在途消息。该取舍需要作为产品决策显式记录，否则会出现"修改模板后消息内容未变化"的反馈。

## 13. Validate 中的网络 I/O

契约要求离线且无副作用，但没有强制手段。将 SMTP 握手放入 `Validate` 在 review 中看起来合理，同时会把接收路径的 p99 推高。

需要通过 lint 规则或 review 检查清单强制，不能只依赖文档注释。

## 14. 时钟偏移

`ClaimDue(now)` 与 `NextAttemptAt` 在 Go 中计算，而 MySQL 在触发器路径中求值 `NOW(3)`。副本时钟偏移可能导致 job 被提前领取，或写入的 `next_attempt_at` 一出生即为过去时。

改进方式：领取查询以数据库时间为准（`FOR UPDATE ... WHERE next_attempt_at <= NOW(3)`），应用时间只用于退避计算。

`Config.Clock` 的注释说明了为什么所有时间戳都需要从它流出：直接读取时钟的组件会与其他组件相差一次调用的耗时。

## 15. tenant_id 当前未使用

它出现在每张表和每个索引前缀中。给在线复合索引补充租户维度需要重建表，因此即使当前未用也保留。代价是每个查询都带有 `tenant_id = ''` 条件，在首次多租户部署前看起来是冗余的。

## 16. MaxAttempts 与 ExpiresAt 的来源

二者是投递级字段，但由消息级配置决定。将 `ExpiresAt` 设为 30 秒的用户，如果其邮件正处于 16 分钟的退避中，会在退避中途变为 `expired`。

这是正确行为，但容易被当作缺陷上报。dispatcher 应计算合理的默认 `ExpiresAt`（例如 `created + 24h`），而非留空表示无限。

## 17. 免打扰 Days 的语义

当前指窗口开始的那天。"仅周末 22:00-08:00"覆盖周六 22:00 至周日 08:00。

这是用户表述"只周末"时的通常含义，但设置界面文案必须与此一致。

## 18. 频控在发送失败时不退还配额

计数发生在 `Evaluate`，消息随后发送失败仍占用额度。使计数与发送原子化不现实。

代价是服务商故障会占用用户当日额度。替代方案（发送成功后再计数）会使突发重试灌水配额。当前选择前者，需要在监控中体现：服务商故障期间"因频控被丢弃的消息数"会异常升高。

## 19. 投诉缺少自动降级

`ComplainedAt` 已记录，但"投诉后自动关闭该用户的营销通道"未实现，需要人工处理。

多数 ESP 要求配置投诉率阈值动作。接入真实服务商前需要补齐，否则发送域会积累信誉问题，其代价是该部署所有后续邮件。

## 20. 邮件已读回执的合规问题

开信像素在部分司法辖区需要用户同意。当前将其记为 `read` 并标注不可靠，但未实现同意管理。面向欧盟用户投产前需要法务确认。

## 21. 模板解析的回退查询

```sql
channel IN (?, '') AND locale IN (?, '') ORDER BY version DESC
```

该查询会 filesort。倾向于使用两次查询而非增加 `template_active` 指针表，但结论取决于模板规模：数百量级时两次查询足够，数万量级时需要指针表。

## 22. 优先级与重试积压的交互未验证

`Priority` 只影响队列服务顺序，不影响重试时机。高优先级消息失败后的退避时间与低优先级相同。

单通道场景下没有问题。高优先级突发与大量重试积压混合时的行为尚未验证，`idx_deliveries_claim` 的列序在该负载下是否最优需要压测确认。
